dsh-fast-compact — the honest, simplified picture

The one-sentence version: the plugin is not a background thread or daemon. It is one object in the host process memory (stored as ctx.compaction) that the host calls when its own events fire. It never waits, polls, or spins. The only state that outlives the process is the session log on disk.

1. Lifecycle with the agent process inside — and where our code kicks in

The frame is the plugin lifecycle (mount → idle object → unmount); the inner box is one agent turn as run by dsh-agent-loop (one user message in → final answer out). Our code only ever appears at the three orange 📍 points — everything else runs with us not involved.

Read the loop direction carefully: SE → PRE is the step cycle. Because 📍A fires at the start of every step, a long turn can compact several times — once per step boundary — and each compaction rewrites the log the next model request is built from. At 📍A the previous step's tool results are already in the log, so the pressure gate always measures the surface after that growth.
